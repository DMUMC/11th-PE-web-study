# ✨ 7주차 주제

---

6주차에서 우리는 드디어 데이터를 **"쓰는"** 서버를 만들었습니다. 

흔히 CRUD라고 말하는 것을 모두 진행해보았습니다!

회원가입으로 회원을 저장하고 평점을 등록하고 수정하고 삭제했죠.

입력 값이 이상하면 **@Valid**나 **ValidationPipe**가 막아줬고 어디서 무슨 문제가 생기든 전역 예외 처리 덕분에 항상 같은 모양의 실패 응답이 돌아왔습니다.

그런데 6주차 API에는 아직 이상한 구석이 하나 있었을 것입니다.

만약, 자신의 계정이 memberId가 1인 사람이 memberId를 2로 수정해서 보내면 어떻게 될까요?

2번 회원의 평점이 등록되고 2번 회원의 평점이 수정되고 2번 회원의 평점이 삭제됩니다. 

서버는 "당신이 2번 회원이 맞나요?"를 한 번도 묻지 않았으니까요.

이건 은행에서 "저 김철수인데요"라고 말하기만 하면 탑승시켜주는 것과 같습니다.

신분증을 확인하는 절차가 통째로 빠져 있는 거예요.

지금까지는 로그인이라는 개념 자체가 없었기 때문에 어쩔 수 없이 **memberId**를 받아왔지만, 이제는 서버가 스스로 "지금 요청을 보낸 사람이 누구인지" 판단할 수 있어야 합니다.

이번 주차에서는 **로그인 API를 만들어 토큰을 발급하고 이후의 모든 요청에서 그 토큰을 검증해
요청자가 누구인지 알아내는 흐름**을 구현합니다.

그 결과 6주차에 만든 평점 API에서 **memberId** 파라미터가 사라지고 남의 평점을 건드리려 하면 서버가 거절하게 됩니다.

여기까지 하고 나면 우리 서비스는 비로소 "내 것"과 "남의 것"을 구분할 줄 아는 서버가 됩니다.

# 📑 7주차 본문 들어가기 전

---

## 1. 7주차에 만들 API 명세

이번 주차에는 API를 세 개 새로 만들고 6주차에 만든 평점 API 세 개를 토큰 기반으로 고칩니다.

**새로 만드는 API**

| API | Method | URL | Request | Success Response |
| --- | --- | --- | --- | --- |
| 로그인 | POST | /auth/login | Body: email, password | {
  "nickname": "영화광",
  "accessToken": "eyJhbGciOi…"
} |
| 내 정보 조회 | GET | /members/me | **Header: Authorization: Bearer {token}** | {
  "email": "movie@umc.com",
  "nickname": "영화광",
  "createdAt": "2026-09-02T21:14:03"
} |
| 내 정보 수정 | PATCH | /members/me | **Header: Authorization: Bearer {token}**
Body: nickname | 내 정보 조회와 동일 |

세 개 모두 성공하면 200 OK입니다.

**6주차 API를 고치는 것**

| API | 6주차 | 7주차 | 무엇이 바뀌나 |
| --- | --- | --- | --- |
| 평점 등록 | POST /members/{memberId}/ratings | POST /ratings | 요청에서 memberId가 사라집니다 |
| 평점 수정 | PATCH /members/{memberId}/ratings/{ratingId} | PATCH /ratings/{ratingId} | 요청에서 memberId가 사라집니다 |
| 평점 삭제 | DELETE /members/{memberId}/ratings/{ratingId} | DELETE /ratings/{ratingId} | 요청에서 memberId가 사라집니다 |

오른쪽이 전부 짧아진 게 보이시나요?

사라진 **memberId**는 이제 요청이 아니라 **토큰**이 알려줍니다.

세 API 모두 헤더에 **Authorization: Bearer {token}**을 함께 보내야 하고 요청 바디는 6주차 그대로입니다.

6주차에도 URL로 memberId를 받았기 때문에 요청 바디에는 memberId가 없었습니다.

하지만, 이번 주차에는 그 자리마저 없어져서 요청 어디에도 "내가 누구인지"를 적는 칸이 남지 않습니다.

성공 상태 코드도 하나 바뀝니다.

6주차 평점 삭제는 **204 No Content** 였는데 이번 주차에는 **200 OK**입니다.

204는 **본문을 보내지 않겠다**는 뜻이라 우리가 5주차부터 약속한 공통 응답 형식을 실어 보낼 수가 없어요.

삭제만 형식에서 빠지는 것을 막으려고 200으로 맞추고 result에 null을 담습니다.

<aside>
💡

**원래는 /auth/login은 우리 원칙에서 벗어난 예외입니다!**

5주차부터 우리는 URL을 **명사형 자원 경로**로 짓기로 했는데, login은 명사가 아니라 동사입니다.

원칙대로라면 "토큰이라는 자원을 만든다"는 뜻으로 POST /auth/tokens가 더 정확해요.

그런데도 /auth/login을 쓰는 건 로그인과 로그아웃을 워낙 많은 서비스가 /login, /logout으로 쓰고 있어서 프론트 개발자가 한눈에 알아본다는 장점이 더 크기 때문입니다.

하지만, **이게 원칙에서 벗어난 예외라는 사실을 알고 쓰는 것**과 **모르고 쓰는 것**은 다릅니다!

</aside>

## 2. 준비물 (의존성과 환경변수)

### **🍃 Spring Boot**

JWT를 만들고 검증하기 위해 jjwt 라이브러리를 추가하겠습니다!

build.gradle의 dependencies 블록 안에 아래 네 줄을 추가해주세요.

```groovy
// build.gradle
dependencies {

    // ... 6주차까지 추가한 의존성은 그대로 두세요 ...
    
    // JWT 생성/검증 라이브러리
    implementation 'io.jsonwebtoken:jjwt-api:0.12.6'
    runtimeOnly 'io.jsonwebtoken:jjwt-impl:0.12.6'
    runtimeOnly 'io.jsonwebtoken:jjwt-jackson:0.12.6'
}
```

그다음 application.yaml에 JWT 설정을 추가합니다.

```yaml
# src/main/resources/application.yaml 의 맨 아래에 추가합니다
jwt:
  secret: ${JWT_SECRET} # 서명에 쓸 비밀키. 코드에 직접 쓰지 않습니다
  access-expiration: ${JWT_ACCESS_EXPIRATION} # 토큰 유효시간(초)
```

실행 환경에 아래 두 값을 넣어주세요.

3주차부터 DB 접속 정보를 넣어온 그 자리입니다.

```
JWT_SECRET=umc-11th-movie-rating-secret-key-please-change-me
JWT_ACCESS_EXPIRATION=3600
```

**JWT_SECRET**은 **최소 32자 이상**이어야 합니다.

**JWT_ACCESS_EXPIRATION**에서 **3600**은 1시간을 **초**로 표현한 값이고 두 스택 모두 초 단위로 맞췄습니다.

### **🐱 NestJS**

NestJS는 JWT 전용 모듈을 공식으로 제공합니다.

```bash
npm install @nestjs/jwt
```

bcrypt는 6주차 회원가입에서 이미 설치했다면 그대로 쓰시면 됩니다.

아직이라면 함께 설치합니다.

```bash
npm install bcrypt
npm install -D @types/bcrypt
```

그다음 .env에 JWT 설정을 추가합니다.

```
JWT_SECRET=umc-11th-movie-rating-secret-key-please-change-me
JWT_ACCESS_EXPIRATION=3600
```

**@nestjs/jwt**의 **expiresIn**은 1h, 30m 같은 문자열 표기도 받지만 환경변수로 읽어온 값은 타입이 맞지 않아 그대로 넘길 수 없습니다.

**초 단위 숫자**로 넘기면 그런 문제가 없고 Spring과 단위도 같아집니다.

**JWT_SECRET**은 짧아도 동작하긴 하지만 짧은 키일수록 추측하기 쉬우니 **32자 이상**으로 넉넉하게 잡아주세요.

마지막으로 app.module.ts에 JwtModule을 등록합니다.

```tsx
// src/app.module.ts
import { Module } from '@nestjs/common';
import { ConfigModule, ConfigService } from '@nestjs/config';
import { JwtModule } from '@nestjs/jwt';

@Module({
  imports: [
    // ... 6주차까지 등록한 모듈(ConfigModule, TypeOrmModule 등)은 그대로 두세요 ...

    JwtModule.registerAsync({
      global: true, // 전역 등록해두면 어느 서비스에서든 JwtService를 주입받을 수 있습니다
      inject: [ConfigService],
      useFactory: (configService: ConfigService) => ({
        secret: configService.get<string>('JWT_SECRET'),
        signOptions: {
          // 초 단위 숫자로 넘깁니다. 환경변수는 문자열로 들어오므로 Number()로 바꿔주세요.
          expiresIn: Number(configService.get<string>('JWT_ACCESS_EXPIRATION') ?? 3600),
        },
      }),
    }),
  ],
  // 6주차까지 등록한 controllers/providers는 그대로 두세요.
  // 아래 실습을 진행하면서 AuthController와 AuthService를 여기에 추가합니다.
})
export class AppModule {}
```

.env 파일과 환경변수에 넣은 JWT_SECRET은 **절대 깃허브에 올리면 안 됩니다!**

앞에서 봤듯이 비밀키를 아는 사람은 원하는 내용으로 토큰을 위조할 수 있기 때문입니다. 

.gitignore에 .env가 들어 있는지 이번 기회에 한 번 더 확인해주세요!

## 3. 실패 응답을 위한 준비 한 가지

6주차에서 우리는 성공이든 실패든 isSuccess/code/message/result 네 개로 감싸서 응답하기로 약속했습니다.

그 약속은 이번 주차에도 그대로 갑니다.

다만… 준비물이 하나 부족해요

이번 주차부터 요청이 거절되는 경우가 갑자기 늘어납니다.

토큰이 없을 때, 토큰이 위조됐을 때, 토큰이 만료됐을 때, 로그인 정보가 틀렸을 때, 그리고 "내 것이 아닌 데이터"를 건드릴 때까지요.

그런데 이 실패들은 대부분 **컨트롤러가 아니라 서비스나 관문 같은 안쪽에서** 발견됩니다.

6주차처럼 컨트롤러에서 ResponseEntity.status(401).body(...)를 직접 만들려면 안쪽에서 알아낸 사실을 바깥까지 일일이 들고 나와야 해요.

그래서 **상태 코드와 코드 문자열 메시지를 함께 담아 던질 수 있는 예외 클래스 하나**를 만듭니다.

어디서 던지든 6주차에 만든 전역 처리기가 받아서 우리 형식으로 바꿔주니 안쪽 코드는 "무엇이 잘못됐는지"만 말하면 됩니다.

6주차에 만든 핸들러들은 **하나도 지우지 않고 그대로 둡니다!**

6주차에 만든 회원가입과 평점 API가 계속 그 핸들러들을 쓰고 있기 때문입니다.

### **🍃 Spring Boot**

먼저 예외 클래스를 만듭니다.

```java
// src/main/java/com/umc/movie/exception/ApiException.java
package com.umc.movie.exception;

import lombok.Getter;
import org.springframework.http.HttpStatus;

@Getter
public class ApiException extends RuntimeException {

    private final HttpStatus status; // 응답으로 내보낼 HTTP 상태 코드
    private final String code;       // 응답 바디의 code 필드에 실릴 문자열

    public ApiException(HttpStatus status, String code, String message) {
        super(message); // message는 부모인 RuntimeException이 들고 있어줍니다
        this.status = status;
        this.code = code;
    }
}
```

다음으로는 6주차에 만든 GlobalExceptionHandler에 아래 메서드를 추가합니다.

```java
// src/main/java/com/umc/movie/controller/GlobalExceptionHandler.java 에 아래 메서드를 추가합니다
// 6주차에 만든 네 개의 핸들러는 그대로 두고 아래 하나만 덧붙이면 됩니다

// 우리가 직접 던진 예외입니다. 예외가 들고 온 상태 코드와 코드 문자열을 그대로 씁니다.
@ExceptionHandler(ApiException.class)
public ResponseEntity<ApiResponse<Void>> handleApiException(ApiException exception) {
    return ResponseEntity.status(exception.getStatus())
            .body(ApiResponse.failure(exception.getCode(), exception.getMessage()));
}
```

파일 상단에 아래 import가 없다면 추가해주세요.

```java
import com.umc.movie.exception.ApiException;
```

**걸리지 않은 응답은 어떻게 처리되나요?**

스프링이 이미 알아서 처리하고 있습니다.

없는 경로는 404, 허용하지 않는 메서드는 405, 형식이 깨진 JSON은 400으로 응답해요.

여기에 **@ExceptionHandler(Exception.class)** 같은 만능 핸들러를 달면 그 정확한 코드들이 전부 500으로 덮여버려서 오히려 원인을 찾기 어려워집니다.

</aside>

### **🐱 NestJS**

NestJS는 UnauthorizedException(401), ForbiddenException(403), NotFoundException(404)처럼 상태 코드별 예외를 이미 갖고 있고 이들은 전부 HttpException의 한 종류라 6주차에 만든 필터가 그대로 잡아줍니다.

우리에게 부족한 건 **코드 문자열을 직접 지정하는 방법** 하나뿐이에요.

```tsx
// src/exception/api.exception.ts
import { HttpException, HttpStatus } from '@nestjs/common';

export class ApiException extends HttpException {
  // code는 응답 바디의 code 필드에 실릴 문자열입니다
  constructor(
    status: HttpStatus,
    public readonly code: string,
    message: string,
  ) {
    super(message, status); // HttpException을 상속하므로 상태 코드는 부모가 들고 있습니다
  }
}
```

이제 6주차에 만든 필터가 이 code를 알아보게 고칩니다.

바뀌는 건 import 한 줄과 code를 정하는 한 줄뿐이에요.

```tsx
// src/filter/http-exception.filter.ts
import { ArgumentsHost, Catch, ExceptionFilter, HttpException } from '@nestjs/common';
import { Response } from 'express';
import { ApiException } from '../exception/api.exception';

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const response = host.switchToHttp().getResponse<Response>();
    const status = exception.getStatus();
    const body = exception.getResponse();
    const message = typeof body === 'string' ? body : (body as { message: string | string[] }).message;

    // ApiException이면 우리가 붙인 코드를 그 외에는 6주차와 같은 규칙을 그대로 씁니다
    const code = exception instanceof ApiException ? exception.code : 'COMMON' + status;

    response.status(status).json({
      isSuccess: false,
      code,
      message: Array.isArray(message) ? message[0] : message,
      result: null,
    });
  }
}
```

main.ts는 그대로 두면 됩니다.

필터의 클래스 이름과 경로를 바꾸지 않았으니 6주차에 등록해둔 app.useGlobalFilters(new HttpExceptionFilter())가 계속 유효해요.

# 🔖 7주차 본문

---

준비물까지 다 챙기고 예외 클래스도 만들어뒀다면, 이제 실제 코드로 들어갈 차례입니다.

먼저 인증과 인가가 무엇인지 JWT가 어떻게 위조를 막는지부터 개념으로 감을 잡겠습니다.

그 다음 **로그인 API**로 토큰을 발급하고 **토큰을 검사하는 공통 관문**을 만들어 컨트롤러 앞에 세웁니다.

이 관문이 준비되면 컨트롤러는 memberId를 그냥 받아 쓰기만 하면 되므로 **내 정보 조회/수정 API**를 아주 짧게 만들 수 있습니다.

마지막으로 6주차에 만든 **평점 CRUD를 토큰 기반으로 리팩토링**하고 남의 평점은 건드릴 수 없도록 **소유권 검증**을 붙입니다.

## 1. 개념: 인증과 인가, 그리고 토큰

### 1) 인증과 인가는 다른 일입니다

혹시 콘서트장을 가보신 적이 있으신가요?

꼭 가수 공연이 아니어도 좋습니다. 운동 경기장이나 학교 축제도 입구 풍경은 비슷하니까요!

떠올려보면 입구에서 직원이 두 가지를 확인합니다.

첫 번째는 **신분 확인**입니다.

예매자 이름과 신분증이 일치하는지 보는 거예요.

"당신이 정말 그 사람이 맞습니까?"를 확인하는 절차입니다.

이게 **인증(Authentication)**입니다.

두 번째는 **팔찌**입니다.

신분증 확인이 끝나면 등급에 맞는 색깔의 팔찌를 채워줍니다.

이후 백스테이지 입구에서 직원은 신분증을 다시 보지 않습니다.

팔찌 색만 보고 "여긴 들어가실 수 없습니다"라고 하죠.

 "당신에게 이 행동을 할 권한이 있습니까?"를 확인하는 절차입니다.

이게 **인가(Authorization)**입니다.

우리 서비스에는 관리자나 VIP 같은 등급이 없습니다.

그래서 이번 주차의 인가는 등급 확인이 아니라 **"이거 네가 쓴 거 맞아?"** 하나예요.

남의 평점은 수정도 삭제도 못 하게 막는 것, 그게 우리가 만들 인가입니다.

| 구분 | 인증 (Authentication) | 인가 (Authorization) |
| --- | --- | --- |
| 질문 | 너 누구야? | 너 이거 해도 돼? |
| 시점 | 로그인할 때 한 번 | 요청할 때마다 |
| 수단 | 이메일 + 비밀번호 | 토큰에 담긴 정보 + 서버의 검사 |
| 실패 | 401 Unauthorized | 403 Forbidden |

> 여기서 상태 코드를 헷갈리기 쉬운데 아주 간단하게 나눌 수 있습니다.
> 
> - **401 Unauthorized**: 네가 누군지 모르겠어. (토큰이 없거나, 위조됐거나, 만료됨)
> - **403 Forbidden**: 네가 누군지는 알겠는데 그건 네 것이 아니야. (남의 평점을 지우려는 경우)

둘 다 이미 겪어보셨을 겁니다.

로그인하지 않은 채로 마이페이지에 들어가려다 로그인 화면으로 튕겨본 적 있으시죠. 그게 401입니다.

로그인은 멀쩡히 했는데 "접근 권한이 없습니다" 문구를 만난 적도 있으실 텐데요. 그게 403이고요.

이름 때문에 401이 "인가 실패"처럼 보이지만, 실제로는 401이 인증 실패이고 403이 인가 실패입니다.

이번 주차 실습에서 두 상황을 직접 만들어보면서 확실히 구분해봅시다.

### 2) 서버가 기억할까요? 손님이 들고 다닐까요?

로그인에 성공한 뒤, 서버는 그 사실을 어딘가에 기억해둬야 합니다.

방법은 크게 두 가지으로 **세션 방식**과 **토큰 방식**으로 나뉘게 됩니다!

- **세션 방식**
    - 식당의 물품 보관함과 비슷합니다.
    - 손님의 짐(로그인 정보)을 식당이 보관함에 넣어두고 손님에게는 번호표만 줍니다.
    - 손님이 번호표를 내밀면 식당이 보관함을 열어 확인하죠.
    - 서버가 모든 로그인 상태를 직접 들고 있어야 하므로 서버가 여러 대로 늘어나면 "내 보관함이 저쪽 서버에 있는데 이쪽 서버로 요청이 갔네" 같은 문제가 생깁니다.
- **토큰 방식**
    - 콘서트장 팔찌와 같습니다.
    - 필요한 정보를 팔찌 자체에 인쇄해서 손님에게 채워 보냅니다.
    - 직원은 팔찌만 보면 되고 명단을 뒤질 필요가 없습니다.
    - 서버가 아무것도 기억하지 않아도 되니 서버를 여러 대로 늘리기 쉽습니다.
    - 대신 한번 채운 팔찌는 되돌려받기 전까지 취소하기 어렵고 팔찌에 인쇄된 내용은 누구나 읽을 수 있습니다.

우리는 **토큰 방식**을 사용할 예정입니다!

### 3) 토큰은 요청의 어디에 실릴까요

팔찌를 만들었으면 이제 어디에 차고 갈지 정해야 합니다.

요청을 편지에 비유하면 지금까지 우리가 다룬 건 **편지지**였습니다.

회원가입할 때 보낸 { "email": ..., "password": ... } 같은 요청 바디를 말하는 겁니다!

그런데 편지에는 봉투도 있죠?

받는 사람 주소, 보내는 사람, 우표, 등기 여부 같이 **배달에 꼭 필요한 정보**가 겉면에 적히죠.

HTTP에서 이 봉투 겉면이 **header**입니다.

요청 한 건은 언제나 헤더와 바디 두 부분으로 되어 있어요.

|  | 무엇을 담나 | 예시 |
| --- | --- | --- |
| 헤더 | 이 요청을 어떻게 다뤄야 하는지 | Content-Type: application/json, Authorization: ... |
| 바디 | 실제로 보내려는 데이터 | { "email": "movie@umc.com" } |

사실 여러분은 이미 헤더를 쓰고 있었습니다.

6주차에 Postman으로 회원가입을 보낼 때 **Content-Type: application/json**이 자동으로 붙었거든요.

"이 바디는 JSON이니 그렇게 읽어라"라고 서버에게 알려주는 헤더입니다.

5주차의 CORS도 서버가 **응답 헤더**에 허용 출처를 적어 보내는 방식이었고요.

토큰은 이 중 **Authorization 헤더**에 싣습니다.

이름 그대로 "나는 이런 자격이 있다"를 적는 칸이에요.

![Authorization.drawio.png](Authorization.drawio.png)

앞에 붙는 Bearer는 "이 토큰을 **지참한 사람**"이라는 뜻의 표준 표기입니다.

Authorization 헤더에는 다른 방식도 올 수 있어서 어떤 방식인지 먼저 밝히고 값을 적는 약속이에요.

Bearer 뒤에 **띄어쓰기 한 칸**이 있다는 점을 기억해두세요.

나중에 토큰을 꺼낼 때는 이 Bearer를 잘라내야 합니다.

<aside>
💡

**왜 바디가 아니라 헤더일까요?**

토큰은 "무엇을 하려는가"가 아니라 "누가 하려는가"에 대한 정보입니다.

편지 내용이 아니라 봉투에 적을 정보라는 뜻이에요.

그리고 **GET**과 **DELETE** 요청은 바디를 쓰지 않는 게 관례라 바디에 토큰을 담으면 조회와 삭제 API에서 토큰을 보낼 방법이 없어집니다.

하지만, 헤더는 모든 메서드에 붙일 수 있기 때문에 **GET**이든 **DELETE**든 상관이 없습니다!

</aside>

### 4) JWT를 직접 뜯어봅시다

JWT(JSON Web Token)는 점으로 구분된 세 덩어리의 문자열입니다.

![token.drawio.png](token.drawio.png)

- **header**
    - 어떤 알고리즘으로 서명했는지
    - (예: {"alg":"HS256"})
- **payload**
    - 담고 싶은 정보
    - (예: {"sub":"1","email":"test@umc.com","exp":1893456000})
- **signature**
    - header와 payload를 비밀키로 서명한 값

여기서 HS256의 HS가 HMAC입니다.

HMAC 서명은 **256비트**

**즉, 32바이트 이상**의 키를 요구해요.

아까 **JWT_SECRET**을 32자 이상으로 잡은 이유가 이겁니다.

그리고 jjwt는 비밀키 길이에 맞춰 알고리즘을 알아서 고릅니다.

32자면 HS256, 48자를 넘으면 HS384예요.

앞에서 드린 예시 키는 48자가 넘으니 잠시 뒤 여러분의 토큰을 뜯어보면 헤더에 HS384가 찍혀 있을 겁니다.

<aside>
🚨

**payload는 암호화된 게 아닙니다!!**

header와 payload는 그냥 Base64URL로 **인코딩**만 되어 있습니다.

암호화가 아니라 인코딩이라서 비밀키가 없는 사람도 디코딩해서 내용을 그대로 읽을 수 있습니다.

 [jwt.io](https://jwt.io/)에 토큰을 붙여넣으면 바로 확인할 수 있어요.

그러니 **비밀번호, 주민번호처럼 남이 보면 안 되는 값은 절대 payload에 넣지 마세요.**

서명이 지켜주는 것은 "내용을 몰래 바꿀 수 없다"는 위조 방지이지 "내용을 못 본다"는 기밀성이 아닙니다.

</aside>

그럼 서명은 왜 필요할까요?

누군가 payload의 "sub":"1"을 "sub":"2"로 바꿔서 2번 회원인 척 하려고 한다고 해봅시다.

내용을 바꾸는 순간 signature와 아귀가 맞지 않게 됩니다.

서버는 받은 header/payload를 자기 비밀키로 다시 서명해보고 그 결과가 토큰에 실려온 signature와 다르면 즉시 거절합니다.

**비밀키를 모르면 유효한 서명을 만들 수 없기 때문에** 위조가 불가능한 거예요.

여기서 자연스럽게 따라오는 결론이 있습니다.

비밀키가 유출되면 누구나 마음대로 토큰을 만들어낼 수 있습니다.

그래서 비밀키는 코드에 직접 쓰지 않고 환경변수로 관리하고 **절대** 깃허브에 올리지 않습니다!

전체 흐름을 그림으로 보면 이렇습니다.

![jwt.drawio.png](jwt.drawio.png)

## 2. 비밀번호는 어떻게 확인할까요?

6주차 회원가입에서 우리는 비밀번호를 bcrypt로 해시해서 저장했습니다.

DB를 열어보면 이런 값이 들어 있을 거예요.

```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
```

여기서 중요한 건 **해시는 되돌릴 수 없다**는 점입니다.

암호화는 열쇠가 있으면 원래 값으로 되돌릴 수 있지만 해시는 애초에 되돌리는 방법이 없습니다.

고기를 갈아 다짐육을 만들면 다시 덩어리로 되돌릴 수 없는 것과 같아요.

그럼 로그인할 때 비밀번호가 맞는지는 어떻게 확인할까요?

되돌리는 대신 **똑같이 갈아서 비교**합니다.

사용자가 입력한 비밀번호를 저장된 해시와 같은 방식으로 해시한 뒤, 두 결과가 같은지만 보는 거예요.

한 가지 더 알아두면 좋은 게 있습니다.

위 해시 문자열을 잘 보면 $2a$10$ 뒤에 22자의 무작위 문자열이 붙어 있는데, 이걸 **salt**라고 합니다.

bcrypt는 해시할 때마다 새로운 salt를 섞기 때문에 같은 비밀번호 Umc1234!를 두 사람이 써도 저장되는 해시 값은 서로 다릅니다.

덕분에 "해시가 같으니 둘이 같은 비밀번호를 쓰는구나"를 알아낼 수 없고 미리 계산해둔 해시 사전으로 뚫는 공격도 막힙니다.

### 🤔 **salt가 매번 달라지면 비교는 어떻게 하나요?**

**정답은 salt가 해시 문자열 안에 같이 들어 있습니다.**

| 조각 | 값 |
| --- | --- |
| 알고리즘과 비용 | $2a$10$ |
| salt (22자) | N9qo8uLOickgx2ZMRZoMye |
| 해시 결과 (31자) | IjZAgcfl7p92ldGxad68LJZdL17lhWy |

그래서 matches()나 compare() 함수는 저장된 값에서 salt를 먼저 꺼내고 그 salt로 입력값을 똑같이 해시한 뒤 결과끼리 비교합니다.

결과적으로 우리는 함수 하나만 호출하면 되고요.

## 3. [실습 1] 로그인 API 만들기 (POST /auth/login)

이제 로그인 API를 만들어봅시다!

하는 일은 세 가지입니다.

이메일로 회원을 찾고 비밀번호를 비교하고 통과하면 토큰을 만들어 돌려줍니다.

<aside>
🚨

**"이메일이 없음"과 "비밀번호가 틀림"을 구분해서 알려주면 안 됩니다**

친절하게 "존재하지 않는 이메일입니다" / "비밀번호가 틀렸습니다"로 나눠서 응답하고 싶어질 텐데 이렇게 하면 공격자가 이메일을 하나씩 넣어보면서 **어떤 이메일이 이 서비스에 가입되어 있는지**를 알아낼 수 있습니다.

가입 여부 자체가 개인정보인 서비스도 많고요.

그래서 로그인 실패는 원인이 무엇이든 **"이메일 또는 비밀번호가 올바르지 않습니다"** 하나로 합쳐서 응답합니다.

아래 코드에서 두 경우 모두 같은 에러 코드를 던지는 이유입니다.

</aside>

### 1) 이번 주차에 쓸 실패 코드를 정해둡니다

앞에서 만든 **ApiException**은 던질 때마다 상태 코드/코드 문자열/메시지 세 가지를 함께 적어줘야 합니다.

실습 도중에 매번 고민하지 않도록, 이번 주차에 쓸 실패 응답을 미리 표로 정해두고 갈게요.

아래 실습에서 예외를 던질 때 이 표를 그대로 옮겨 적으시면 됩니다.

| 상황 | 상태 | code | message |
| --- | --- | --- | --- |
| 로그인 정보가 틀림 | 401 | `AUTH401_1` | 이메일 또는 비밀번호가 올바르지 않습니다. |
| 토큰이 아예 없음 | 401 | `AUTH401_2` | 로그인이 필요한 요청입니다. |
| 토큰이 위조됨 | 401 | `AUTH401_3` | 유효하지 않은 토큰입니다. |
| 토큰이 만료됨 | 401 | `AUTH401_4` | 토큰이 만료되었습니다. 다시 로그인해주세요. |
| 회원을 찾을 수 없음 | 404 | `MEMBER404_1` | 해당 회원을 찾을 수 없습니다. |
| 닉네임이 이미 쓰이는 중 | 409 | `MEMBER409_1` | 이미 사용 중인 닉네임입니다. |
| 평점을 찾을 수 없음 | 404 | `RATING404_1` | 해당 평점을 찾을 수 없습니다. |
| 남의 평점을 건드림 | 403 | `RATING403_1` | 본인이 작성한 평점만 수정하거나 삭제할 수 있습니다. |
| 같은 영화에 평점을 또 남김 | 409 | `RATING409_1` | 이미 이 영화에 평점을 남기셨습니다. |

코드 문자열을 AUTH401_1, RATING403_1처럼 짓는 규칙에 주목해주세요.

{도메인}{HTTP 상태 코드}_{일련번호} 형태라서 프론트 개발자가 AUTH401_4라는 코드만 보고도 "인증 쪽에서 401이 났고 그중 네 번째 사유구나"를 바로 알 수 있습니다.

6주차에는 실패가 몇 종류 되지 않아 COMMON4091 정도로 충분했지만 이번 주차처럼 401만 네 가지가 되면 도메인과 사유를 구분해줄 필요가 생깁니다.

표에 성공 코드가 없는 게 이상하실 수 있는데, 성공 응답은 6주차에 만든 성공 값을 그대로 사용합니다.

그래서 성공은 계속 COMMON200/COMMON201이고 무슨 일이 성공했는지는 message가 알려줍니다.

실패만 사유가 여러 갈래로 갈라지기 때문에 코드를 세분화하는 거예요.

```java
// src/main/java/com/umc/movie/util/JwtUtil.java
package com.umc.movie.util;

import com.umc.movie.exception.ApiException;
import io.jsonwebtoken.Claims;
import io.jsonwebtoken.ExpiredJwtException;
import io.jsonwebtoken.Jws;
import io.jsonwebtoken.JwtException;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Component;

import javax.crypto.SecretKey;
import java.nio.charset.StandardCharsets;
import java.time.Duration;
import java.time.Instant;
import java.util.Date;

@Component
public class JwtUtil {

    private final SecretKey secretKey;
    private final Duration accessExpiration;

    public JwtUtil(
            @Value("${jwt.secret}") String secret,
            @Value("${jwt.access-expiration}") Long accessExpiration
    ) {
        // 문자열 비밀키를 HMAC-SHA 서명용 키 객체로 바꿉니다.
        // 이 키가 있어야만 서명을 만들 수 있고 같은 키로만 검증할 수 있습니다.
        this.secretKey = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
        this.accessExpiration = Duration.ofSeconds(accessExpiration);
    }

    /**
     * 로그인에 성공한 회원에게 발급할 Access Token을 만듭니다.
     */
    public String createAccessToken(Long memberId, String email) {
        Instant now = Instant.now();

        return Jwts.builder()
                .subject(String.valueOf(memberId)) // 토큰의 주인이 누구인지. 우리는 memberId를 넣습니다
                .claim("email", email)             // 참고용 부가 정보 (없어도 동작합니다)
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plus(accessExpiration))) // 만료 시각이 없으면 영원히 유효한 토큰이 됩니다
                .signWith(secretKey)               // 이 서명 덕분에 내용을 조작하면 검증에서 걸립니다
                .compact();
    }

    /**
     * 토큰을 검증하고 그 안에 담긴 memberId를 꺼냅니다.
     * 서명이 맞지 않거나 만료된 토큰이면 예외를 던지므로 이 메서드가 값을 돌려줬다면
     * "검증까지 통과한 토큰"이라는 뜻입니다.
     */
    public Long getMemberId(String token) {
        try {
            return Long.valueOf(getClaims(token).getPayload().getSubject());
        } catch (ExpiredJwtException e) {
            // 만료는 사용자가 다시 로그인하면 해결되는 상황이라 따로 구분해줍니다
            throw new ApiException(HttpStatus.UNAUTHORIZED, "AUTH401_4",
                    "토큰이 만료되었습니다. 다시 로그인해주세요.");
        } catch (JwtException | IllegalArgumentException e) {
            // 서명 불일치, 형식 오류 등 그 외 모든 실패
            throw new ApiException(HttpStatus.UNAUTHORIZED, "AUTH401_3",
                    "유효하지 않은 토큰입니다.");
        }
    }

    private Jws<Claims> getClaims(String token) {
        return Jwts.parser()
                .verifyWith(secretKey)  // 이 키로 서명을 다시 계산해서 대조합니다
                .clockSkewSeconds(60)   // 서버와 클라이언트 시계가 조금 어긋나도 되도록 60초 여유를 둡니다
                .build()
                .parseSignedClaims(token);
    }
}
```

```java
// src/main/java/com/umc/movie/service/AuthService.java
package com.umc.movie.service;

import com.umc.movie.dto.LoginRequest;
import com.umc.movie.dto.LoginResponse;
import com.umc.movie.entity.Member;
import com.umc.movie.exception.ApiException;
import com.umc.movie.repository.MemberRepository;
import com.umc.movie.util.JwtUtil;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class AuthService {

    private final MemberRepository memberRepository;
    private final PasswordEncoder passwordEncoder; // 6주차 회원가입에서 등록해둔 Bean입니다
    private final JwtUtil jwtUtil;

    public LoginResponse login(LoginRequest request) {
        // 1. 이메일로 회원을 찾습니다.
        //    없어도 "가입되지 않은 이메일"이라고 알려주지 않고 아래와 같은 예외를 던집니다.
        Member member = memberRepository.findByEmail(request.email())
                .orElseThrow(() -> new ApiException(HttpStatus.UNAUTHORIZED, "AUTH401_1",
                        "이메일 또는 비밀번호가 올바르지 않습니다."));

        // 2. 입력한 비밀번호를 저장된 해시와 비교합니다.
        //    matches()가 저장된 해시에서 salt를 꺼내 같은 방식으로 해시한 뒤 대조해줍니다.
        if (!passwordEncoder.matches(request.password(), member.getPassword())) {
            throw new ApiException(HttpStatus.UNAUTHORIZED, "AUTH401_1",
                    "이메일 또는 비밀번호가 올바르지 않습니다.");
        }

        // 3. 검증을 통과했으니 토큰을 발급합니다.
        String accessToken = jwtUtil.createAccessToken(member.getMemberId(), member.getEmail());

        return new LoginResponse(member.getNickname(), accessToken);
    }
}
```

```tsx
// src/service/auth.service.ts
import { HttpStatus, Injectable } from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import * as bcrypt from 'bcrypt';
import { Member } from '../entity/member.entity';
import { LoginRequestDto } from '../dto/login-request.dto';
import { LoginResponseDto } from '../dto/login-response.dto';
import { ApiException } from '../exception/api.exception';

@Injectable()
export class AuthService {
  constructor(
    @InjectRepository(Member)
    private readonly memberRepository: Repository<Member>,
    private readonly jwtService: JwtService,
  ) {}

  async login(dto: LoginRequestDto): Promise<LoginResponseDto> {
    // 1. 이메일로 회원을 찾습니다.
    //    없어도 "가입되지 않은 이메일"이라고 알려주지 않고 아래와 같은 예외를 던집니다.
    const member = await this.memberRepository.findOne({
      where: { email: dto.email },
    });

    if (!member) {
      throw new ApiException(
        HttpStatus.UNAUTHORIZED,
        'AUTH401_1',
        '이메일 또는 비밀번호가 올바르지 않습니다.',
      );
    }

    // 2. 입력한 비밀번호를 저장된 해시와 비교합니다.
    //    compare()가 저장된 해시에서 salt를 꺼내 같은 방식으로 해시한 뒤 대조해줍니다.
    const isPasswordMatched = await bcrypt.compare(dto.password, member.password);

    if (!isPasswordMatched) {
      throw new ApiException(
        HttpStatus.UNAUTHORIZED,
        'AUTH401_1',
        '이메일 또는 비밀번호가 올바르지 않습니다.',
      );
    }

    // 3. 검증을 통과했으니 토큰을 발급합니다.
    //    sub는 JWT 표준에서 "이 토큰의 주인"을 뜻하는 항목입니다.
    const accessToken = await this.jwtService.signAsync({
      sub: String(member.memberId),
      email: member.email,
    });

    return {
      nickname: member.nickname,
      accessToken,
    };
  }
}
```

## 4. [실습 2] 토큰을 검사하는 관문 만들기

토큰은 발급했지만, 아직 아무도 그 토큰을 확인해주지 않습니다.

이제 검사하는 쪽을 만들 차례입니다.

여기서 잠깐 생각해봅시다.

토큰 검사 코드를 어디에 둬야 할까요?

컨트롤러마다 맨 앞에 넣는 방법도 있지만, API가 20개면 같은 코드를 20번 복사해야 하고 하나라도 빠뜨리면 그 API만 문이 열려버립니다.

그래서 **컨트롤러에 도달하기 전에 모든 요청이 반드시 지나가는 길목**에 검사대를 세웁니다.

건물 로비의 출입 게이트를 떠올리시면 됩니다.

사무실 문마다 경비를 세우는 대신 로비 게이트 하나로 거르는 거예요.

![intercepter.drawio.png](intercepter.drawio.png)

Spring은 이 역할을 하는 도구로 **HandlerInterceptor**를 NestJS는 **Guard**를 제공합니다.

이름은 다르지만 "컨트롤러 앞에서 요청을 들여보낼지 말지 결정한다"는 역할은 똑같습니다.

관문이 하는 일은 세 가지입니다.

> 
> 
> 1. Authorization 헤더에서 토큰을 꺼낸다.
> 2. 토큰을 검증하고 memberId를 알아낸다.
> 3. 알아낸 memberId를 요청에 담아둬서 뒤이어 실행될 컨트롤러가 꺼내 쓸 수 있게 한다.

3번이 핵심입니다.

관문이 신원 확인을 끝내고 그 결과를 요청에 붙여두기 때문에 컨트롤러는 토큰이 뭔지도 모른 채 memberId만 받아 쓰면 됩니다.

#### **🍃 Spring Boot**

```java
// src/main/java/com/umc/movie/interceptor/AuthInterceptor.java
package com.umc.movie.interceptor;

import com.umc.movie.exception.ApiException;
import com.umc.movie.util.JwtUtil;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpMethod;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

@Component
@RequiredArgsConstructor
public class AuthInterceptor implements HandlerInterceptor {

    public static final String MEMBER_ID = "memberId"; // 컨트롤러에서 꺼낼 때 쓸 이름
    private static final String BEARER_PREFIX = "Bearer ";

    private final JwtUtil jwtUtil;

    /**
     * 컨트롤러가 실행되기 "전"에 호출됩니다.
     * true를 반환하면 요청이 컨트롤러까지 이어지고 예외를 던지면 여기서 끝납니다.
     */
    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler
    ) {
        // 브라우저가 본 요청 전에 보내는 CORS 사전 요청(preflight)에는 토큰이 붙지 않습니다.
        // 여기서 막아버리면 브라우저에서 오는 모든 요청이 실패하므로 그냥 통과시킵니다.
        if (HttpMethod.OPTIONS.matches(request.getMethod())) {
            return true;
        }

        String header = request.getHeader(HttpHeaders.AUTHORIZATION);

        // "Bearer {토큰}" 형식이 아니면 아예 토큰을 보내지 않은 것으로 봅니다
        if (header == null || !header.startsWith(BEARER_PREFIX)) {
            throw new ApiException(HttpStatus.UNAUTHORIZED, "AUTH401_2",
                    "로그인이 필요한 요청입니다.");
        }

        // 검증에 실패하면 JwtUtil이 예외를 던지므로 여기까지 왔다면 유효한 토큰입니다
        Long memberId = jwtUtil.getMemberId(header.substring(BEARER_PREFIX.length()));

        // 뒤이어 실행될 컨트롤러가 꺼내 쓸 수 있도록 요청에 담아둡니다
        request.setAttribute(MEMBER_ID, memberId);

        return true;
    }
}
```

#### **🐱 NestJS**

```tsx
// src/guard/auth.guard.ts
import { CanActivate, ExecutionContext, HttpStatus, Injectable } from '@nestjs/common';
import { JwtService, TokenExpiredError } from '@nestjs/jwt';
import type { Request } from 'express'; // 데코레이터 시그니처에 쓰는 타입은 import type 이어야 합니다
import { ApiException } from '../exception/api.exception';

const BEARER_PREFIX = 'Bearer ';

@Injectable()
export class AuthGuard implements CanActivate {
  constructor(private readonly jwtService: JwtService) {}

  /**
   * 컨트롤러가 실행되기 "전"에 호출됩니다.
   * true를 반환하면 요청이 컨트롤러까지 이어지고 예외를 던지면 여기서 끝납니다.
   */
  async canActivate(context: ExecutionContext): Promise<boolean> {
    const request = context.switchToHttp().getRequest<Request>();
    const header = request.headers.authorization;

    // "Bearer {토큰}" 형식이 아니면 아예 토큰을 보내지 않은 것으로 봅니다
    if (!header || !header.startsWith(BEARER_PREFIX)) {
      throw new ApiException(
        HttpStatus.UNAUTHORIZED,
        'AUTH401_2',
        '로그인이 필요한 요청입니다.',
      );
    }

    const token = header.slice(BEARER_PREFIX.length);

    try {
      // 서명과 만료 시각을 함께 검증합니다. 실패하면 예외가 납니다.
      const payload = await this.jwtService.verifyAsync<{ sub: string; email: string }>(token);

      // 뒤이어 실행될 컨트롤러가 꺼내 쓸 수 있도록 요청 객체에 담아둡니다.
      // sub는 문자열로 저장되므로 숫자로 바꿔줍니다.
      request['memberId'] = Number(payload.sub);
    } catch (error) {
      // 만료는 사용자가 다시 로그인하면 해결되는 상황이라 따로 구분해줍니다
      if (error instanceof TokenExpiredError) {
        throw new ApiException(
          HttpStatus.UNAUTHORIZED,
          'AUTH401_4',
          '토큰이 만료되었습니다. 다시 로그인해주세요.',
        );
      }
      throw new ApiException(
        HttpStatus.UNAUTHORIZED,
        'AUTH401_3',
        '유효하지 않은 토큰입니다.',
      );
    }

    return true;
  }
}
```

NestJS의 Guard는 **@UseGuards(AuthGuard)**를 붙인 컨트롤러나 메서드에만 적용됩니다.

즉, Spring처럼 "전부 잠그고 예외를 여는" 방식이 아니라 **로그인이 필요한 곳에 하나씩 붙이는 방식**입니다.

아래 실습에서 컨트롤러마다 이 데코레이터를 붙이게 되니 새 API를 만들 때 빠뜨리지 않도록 주의해주세요.

여기까지 만들었다면 관문은 완성입니다.

앞으로 만드는 컨트롤러는 **토큰을 전혀 몰라도 됩니다.**

**Postman으로 확인해봅시다.**

GET /members/me를 세 가지 방식으로 호출해보세요.

1. 헤더 없이 그냥 호출 → 401, AUTH401_2 (로그인이 필요한 요청입니다)
2. Authorization 탭에서 Type을 Bearer Token으로 고르고 실습 1에서 받은 토큰을 붙여넣기 → 200과 내 정보
3. 토큰 **가운데 부분(payload)의 아무 글자나 하나를 다른 글자로 바꿔서** 호출 → 401, AUTH401_3 (유효하지 않은 토큰입니다)

3번이 바로 앞에서 이야기한 서명 검증입니다.

한 글자만 바꿔도 서명이 맞지 않게 되어 서버가 즉시 걸러냅니다.

직접 해보시면 "위조가 불가능하다"는 말이 훨씬 실감납니다.

<aside>
💡

**글자를 "덧붙이지" 말고 "바꿔"주세요**

토큰 맨 뒤에 글자 하나를 덧붙이는 방식으로 시도하면 **오히려 통과해버릴 수 있습니다.**

서명 부분은 Base64로 인코딩되어 있는데, 뒤에 붙은 자투리 문자가 디코딩 과정에서 버려져 원래와 같은 값이 되는 경우가 있거든요.

서명이 고장난 게 아니라 "덧붙인 글자가 없는 것과 같아진" 것입니다.

있던 글자를 **다른 글자로 교체**하면 확실하게 401이 납니다.

payload 가운데를 바꾸면 "내용을 조작하면 걸린다"는 것도 함께 보여서 더 좋습니다.

</aside>

```tsx
async updateMyInfo(
  memberId: number,
  dto: MemberUpdateRequestDto,
): Promise<MemberInfoResponseDto> {
  const member = await this.memberRepository.findOne({
    where: { memberId },
  });

  if (!member) {
    throw new ApiException(
      HttpStatus.NOT_FOUND,
      'MEMBER404_1',
      '해당 회원을 찾을 수 없습니다.',
    );
  }

  // 나를 제외한 다른 회원이 그 닉네임을 쓰고 있다면 막습니다.
  // DB에도 UNIQUE 제약이 걸려 있지만, 제약 위반 예외 대신 우리가 정한 응답을 주기 위해 먼저 확인합니다.
  const duplicated = await this.memberRepository.findOne({
    where: { nickname: dto.nickname, memberId: Not(memberId) },
  });

  if (duplicated) {
    throw new ApiException(
      HttpStatus.CONFLICT,
      'MEMBER409_1',
      '이미 사용 중인 닉네임입니다.',
    );
  }

  member.nickname = dto.nickname;
```

## 7. [실습 5] 평점 CRUD를 토큰 기반으로 리팩토링하기

드디어 이번 주차의 목적지입니다.

6주차에 만든 평점 등록/수정/삭제 API에서 memberId를 걷어냅니다.

바뀌는 부분을 먼저 정리해볼게요.

| 구분 | 6주차 (before) | 7주차 (after) |
| --- | --- | --- |
| 등록 | POST /members/{memberId}/ratings | POST /ratings |
| 수정 | PATCH /members/{memberId}/ratings/{ratingId} | PATCH /ratings/{ratingId} |
| 삭제 | DELETE /members/{memberId}/ratings/{ratingId} | DELETE /ratings/{ratingId} |
| 누구인지 | 클라이언트가 알려줌 | 서버가 토큰에서 알아냄 |

URL에서 /members/{memberId} 부분이 통째로 사라진 게 보이시나요?

등록 API의 주소가 짧아진 건 단순히 보기 좋아서가 아닙니다.

**URL에 남아 있으면 클라이언트가 그 값을 바꿔 보낼 수 있기 때문**입니다.

값을 받지 않는 것이 곧 그 값을 조작당하지 않는 방법입니다.

한편 5주차에 만든 유저별 평점 조회(GET /members/{memberId}/ratings)는 **그대로 둡니다.**

이건 "특정 회원이 남긴 평점 목록"을 누구나 볼 수 있게 하는 공개 기능이라 로그인한 본인만 볼 수 있어야 하는 기능이 아니기 때문입니다.

앞에서 인터셉터의 예외 목록에 이 경로를 넣어둔 이유이기도 합니다.

#### **🍃 Spring Boot**

**요청 DTO는 6주차에서 만든 것을 그대로 씁니다.**

CreateRatingRequest와 UpdateRatingRequest 둘 다 손댈 필요가 없어요.

애초에 이 DTO들은 memberId를 받은 적이 없거든요.

6주차에서는 memberId를 **URL 경로로** 받았기 때문에 이번 주차에 걷어낼 것도 바디가 아니라 URL입니다.

응답 DTO는 5주차, Rating 엔티티의 update()와 RatingRepository의 중복 확인 메서드는 6주차에서 이미 만들어뒀으니 전부 그대로 씁니다.

바뀌는 건 **Service의 예외**, **Controller의 URL과 memberId 출처**, 그리고 **평점 등록의 응답** 세 가지입니다.

6주차에는 평점 등록이 result에 ratingId 숫자만 담아 돌려줬는데, 이번 주차에는 평점 수정과 똑같이 RatingResponse를 담습니다.

위 명세의 예시 응답이 그 모습이에요.

Service부터 봅시다.

하는 일은 6주차와 똑같고 6주차에서 ResponseStatusException과 IllegalArgumentException으로 던지던 실패를 이번 주차의 ApiException으로 바꿉니다.

그래야 앞에서 정해둔 RATING403_1 같은 코드를 실어 보낼 수 있습니다.

```java
// src/main/java/com/umc/movie/service/RatingService.java
package com.umc.movie.service;

import com.umc.movie.dto.CreateRatingRequest;
import com.umc.movie.dto.RatingResponse;
import com.umc.movie.dto.UpdateRatingRequest;
import com.umc.movie.entity.Member;
import com.umc.movie.entity.Rating;
import com.umc.movie.exception.ApiException;
import com.umc.movie.repository.MemberRepository;
import com.umc.movie.repository.RatingRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;

@Service
@RequiredArgsConstructor
public class RatingService {

    private final RatingRepository ratingRepository;
    private final MemberRepository memberRepository;

    // 5주차에 만든 조회입니다. 예외만 ApiException으로 바꿨습니다.
    @Transactional(readOnly = true)
    public List<RatingResponse> getRatingsByMember(Long memberId) {
        if (!memberRepository.existsById(memberId)) {
            throw new ApiException(HttpStatus.NOT_FOUND, "MEMBER404_1",
                    "해당 회원을 찾을 수 없습니다.");
        }

        return ratingRepository.findByMember_MemberIdOrderByRatingIdDesc(memberId).stream()
                .map(RatingResponse::from)
                .toList();
    }

    @Transactional
    public RatingResponse create(Long memberId, CreateRatingRequest request) {
        Member member = memberRepository.findById(memberId)
                .orElseThrow(() -> new ApiException(HttpStatus.NOT_FOUND, "MEMBER404_1",
                        "해당 회원을 찾을 수 없습니다."));

        if (ratingRepository.existsByMember_MemberIdAndMovieId(memberId, request.movieId())) {
            throw new ApiException(HttpStatus.CONFLICT, "RATING409_1",
                    "이미 이 영화에 평점을 남기셨습니다.");
        }

        Rating rating = Rating.builder()
                .member(member)
                .movieId(request.movieId())
                .score(request.score())
                .comment(request.comment())
                .build();

        return RatingResponse.from(ratingRepository.save(rating));
    }

    @Transactional
    public RatingResponse update(Long memberId, Long ratingId, UpdateRatingRequest request) {
        Rating rating = findOwnedRating(memberId, ratingId);

        rating.update(request.score(), request.comment());
        ratingRepository.save(rating);

        return RatingResponse.from(rating);
    }

    @Transactional
    public void delete(Long memberId, Long ratingId) {
        Rating rating = findOwnedRating(memberId, ratingId);

        ratingRepository.delete(rating);
    }

    /**
     * 평점을 찾고 그 평점이 요청자의 것인지까지 확인합니다.
     * 수정과 삭제가 똑같은 검사를 하므로 메서드로 묶었습니다.
     */
    private Rating findOwnedRating(Long memberId, Long ratingId) {
        Rating rating = ratingRepository.findById(ratingId)
                .orElseThrow(() -> new ApiException(HttpStatus.NOT_FOUND, "RATING404_1",
                        "해당 평점을 찾을 수 없습니다."));

        // 존재는 하지만 내 것이 아니라면 인가 실패입니다
        if (!rating.getMember().getMemberId().equals(memberId)) {
            throw new ApiException(HttpStatus.FORBIDDEN, "RATING403_1",
                    "본인이 작성한 평점만 수정하거나 삭제할 수 있습니다.");
        }

        return rating;
    }
}
```

이 DTO들은 memberId를 받은 적이 없거든요.

6주차에서는 memberId를 **URL 경로로** 받았기 때문에, 이번 주차에 걷어낼 것도 바디가 아니라 URL입니다.

응답 DTO는 5주차에서 만든 것을 그대로 씁니다.

바뀌는 건 **Service의 예외**, **Controller의 URL과 memberId 출처**, 그리고 **평점 등록의 응답** 세 가지입니다.

6주차에는 평점 등록이 result에 ratingId 숫자만 담아 돌려줬는데, 이번 주차에는 평점 수정과 똑같이 RatingResponseDto를 담습니다.

```tsx
// src/service/rating.service.ts
import { HttpStatus, Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Member } from '../entity/member.entity';
import { Rating } from '../entity/rating.entity';
import { CreateRatingDto } from '../dto/create-rating.dto';
import { UpdateRatingDto } from '../dto/update-rating.dto';
import { RatingResponseDto } from '../dto/rating-response.dto';
import { ApiException } from '../exception/api.exception';

@Injectable()
export class RatingService {
  constructor(
    @InjectRepository(Rating)
    private readonly ratingRepository: Repository<Rating>,
    @InjectRepository(Member)
    private readonly memberRepository: Repository<Member>,
  ) {}

  // 5주차에 만든 조회입니다. 예외만 ApiException으로 바꿨습니다.
  async getRatingsByMember(memberId: number): Promise<RatingResponseDto[]> {
    const member = await this.memberRepository.findOneBy({ memberId });
    if (!member) {
      throw new ApiException(
        HttpStatus.NOT_FOUND,
        'MEMBER404_1',
        '해당 회원을 찾을 수 없습니다.',
      );
    }

    const ratings = await this.ratingRepository.find({
      where: { member: { memberId } },
      order: { ratingId: 'DESC' },
    });

    return ratings.map(RatingResponseDto.from);
  }

  async create(memberId: number, dto: CreateRatingDto): Promise<RatingResponseDto> {
    const member = await this.memberRepository.findOneBy({ memberId });
    if (!member) {
      throw new ApiException(
        HttpStatus.NOT_FOUND,
        'MEMBER404_1',
        '해당 회원을 찾을 수 없습니다.',
      );
    }

    const existing = await this.ratingRepository.findOne({
      where: { member: { memberId }, movieId: dto.movieId },
    });
    if (existing) {
      throw new ApiException(
        HttpStatus.CONFLICT,
        'RATING409_1',
        '이미 이 영화에 평점을 남기셨습니다.',
      );
    }

    const saved = await this.ratingRepository.save(
      this.ratingRepository.create({
        member,
        movieId: dto.movieId,
        score: dto.score,
        comment: dto.comment ?? null,
      }),
    );

    return RatingResponseDto.from(saved);
  }

  async update(
    memberId: number,
    ratingId: number,
    dto: UpdateRatingDto,
  ): Promise<RatingResponseDto> {
    const rating = await this.findOwnedRating(memberId, ratingId);

    rating.score = dto.score;
    rating.comment = dto.comment ?? null;

    const saved = await this.ratingRepository.save(rating);
    return RatingResponseDto.from(saved);
  }

  async delete(memberId: number, ratingId: number): Promise<void> {
    const rating = await this.findOwnedRating(memberId, ratingId);

    await this.ratingRepository.remove(rating);
  }

  /**
   * 평점을 찾고 그 평점이 요청자의 것인지까지 확인합니다.
   * 수정과 삭제가 똑같은 검사를 하므로 메서드로 묶었습니다.
   */
  private async findOwnedRating(memberId: number, ratingId: number): Promise<Rating> {
    const rating = await this.ratingRepository.findOne({
      where: { ratingId },
      relations: { member: true }, // 작성자를 함께 불러와야 소유권을 비교할 수 있습니다
    });

    if (!rating) {
      throw new ApiException(
        HttpStatus.NOT_FOUND,
        'RATING404_1',
        '해당 평점을 찾을 수 없습니다.',
      );
    }

    // 존재는 하지만 내 것이 아니라면 인가 실패입니다
    if (rating.member.memberId !== memberId) {
      throw new ApiException(
        HttpStatus.FORBIDDEN,
        'RATING403_1',
        '본인이 작성한 평점만 수정하거나 삭제할 수 있습니다.',
      );
    }

    return rating;
  }
}
```

</aside>

"내용 없음"이라 응답 바디를 보내면 안 되는 상태 코드인데, 우리는 모든 응답을 isSuccess/code/ message 형태로 감싸서 보내기로 했기 때문에 바디가 항상 존재합니다.

그래서 삭제는 200을 쓰고 result만 null로 둡니다. 상태 코드의 규칙과 우리 프로젝트의 응답 규칙이 충돌할 때, 어느 쪽을 어떤 이유로 택했는지 알고 있는 것이 중요합니다.

## 8. [실습 6] 401과 403을 직접 만들어보기

**findOwnedRating**에서 조용히 지나간 부분을 다시 봅시다.

```java
// 없는 평점을 수정하려는 경우
throw new ApiException(HttpStatus.NOT_FOUND, "RATING404_1",
        "해당 평점을 찾을 수 없습니다.");

// 존재하지만 내 것이 아닌 평점을 수정하려는 경우
throw new ApiException(HttpStatus.FORBIDDEN, "RATING403_1",
        "본인이 작성한 평점만 수정하거나 삭제할 수 있습니다.");
```

이 두 줄이 이번 주차 학습 목표 중 "로그인한 본인의 데이터만 수정/삭제한다"를 실제로 지켜내는 코드입니다.

관문(인터셉터/Guard)은 "당신이 누구인지"까지만 확인해줄 뿐, "이 평점이 당신 것인지"는 확인해주지 않습니다.

**인증은 공통 관문에서 인가는 서비스에서** 처리하는 이 분담을 기억해주세요.

평점이 내 것인지 아닌지는 DB를 조회해봐야 알 수 있는 그 기능만의 고유한 규칙이기 때문입니다.

404와 403의 순서에도 이유가 있습니다.

먼저 평점을 찾아보고(없으면 404) 찾았으면 그다음에 주인이 누구인지 봅니다(내 것이 아니면 403). 

반대로 하면 애초에 존재하지도 않는 평점에 대해 "권한이 없습니다"라고 답하게 되어 앞뒤가 맞지 않아요.

<aside>
💡

**403 대신 404를 주는 선택지도 있습니다**

"남의 평점을 수정하려 했다"는 403 응답은 뒤집어 보면 **그 번호의 평점이 존재한다는 사실**을 알려주는 셈입니다.

그래서 서비스에 따라서는 남의 것에도 일부러 404를 돌려줘서 존재 여부 자체를 숨기기도 합니다.

우리는 학습 목적상 401과 403의 차이를 눈으로 보는 게 더 중요하므로 403을 그대로 씁니다.

다만 이런 트레이드오프가 있다는 것은 알아두시면 좋아요.

</aside>

세 가지 실패를 직접 만들어보면서 차이를 확인해봅시다.

| 만드는 방법 | 결과 | code | 왜 그런가 |
| --- | --- | --- | --- |
| Authorization 헤더를 빼고 요청 | 401 | AUTH401_2 | 서버가 요청자를 특정할 수 없음 |
| 다른 회원의 토큰으로 남의 평점 수정 | 403 | RATING403_1 | 요청자는 알지만 그 데이터가 남의 것 |
| 없는 ratingId로 삭제 | 404 | RATING404_1 | 대상 자체가 존재하지 않음 |

가운데 줄이 이번 주차의 하이라이트입니다.

**토큰은 멀쩡한데도 막힌다**는 점이 인증과 인가가 서로 다른 일이라는 가장 확실한 증거예요.

## 9. Postman으로 전체 시나리오를 검증합시다

코드가 다 됐으면 이제 시나리오로 확인할 차례입니다.

**회원을 두 명 만들어두는 것**이 핵심입니다. 혼자서는 403을 만들어볼 수 없으니까요.

> 
> 
> 1. **준비**: 6주차 회원가입 API로 A(a@umc.com), B(b@umc.com) 두 명을 가입시킵니다.
> 2. **로그인**: A로 로그인해서 토큰 A, B로 로그인해서 토큰 B를 각각 받아둡니다.
> 3. **등록**: 토큰 A로 POST /ratings를 호출해 평점을 등록합니다. 응답의 result.ratingId를
> 기억해두세요. 201과 COMMON201이 돌아오면 성공입니다.
> 4. **중복 등록**: 똑같은 movieId로 한 번 더 등록해봅니다. 409, RATING409_1이 돌아와야 합니다.
> DB의 복합 UNIQUE 제약을 우리가 먼저 잡아낸 결과입니다.
> 5. **본인 수정**: 토큰 A로 PATCH /ratings/{3번에서 받은 ratingId}를 호출합니다. (200)
> 6. **남의 것 수정 (403)**: **토큰만 B로 바꿔서** 똑같은 요청을 보냅니다. (403, RATING403_1)
> 토큰은 멀쩡한데도 막혔다는 점이 중요합니다. 인증은 통과했지만 인가에서 걸린 거예요.
> 7. **토큰 없이 (401)**: Authorization 헤더를 지우고 보냅니다. (401, AUTH401_2)
> 8. **없는 평점 (404)**: 토큰 A로 DELETE /ratings/99999를 호출합니다. (404, RATING404_1)
> 9. **본인 삭제**: 토큰 A로 3번의 평점을 삭제합니다. (200, COMMON200)

6번과 7번의 차이를 특히 눈여겨봐 주세요.

둘 다 "요청이 거절됐다"는 결과는 같지만, 서버가 거절한 이유는 전혀 다릅니다.

프론트 입장에서도 401이면 로그인 화면으로 보내야 하고 403이면 "권한이 없습니다" 안내를 띄워야 하니 반드시 구분되어야 하는 정보입니다.

![auth.drawio.png](auth.drawio.png)

여기까지 완주하셨다면 우리 서버는 이제 "누가 무엇을 할 수 있는지"를 스스로 판단합니다.

8주차에서는 이 위에 서비스의 핵심 기능을 얹으면서 여러 데이터가 한꺼번에 바뀔 때 중간에 실패하면 어떻게 되는지 그리고 트랜잭션이 그걸 어떻게 해결하는지를 다룹니다.
